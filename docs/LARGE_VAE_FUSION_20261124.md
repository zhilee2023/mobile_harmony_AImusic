# 较大模型VAE融合：同输入验证与入口修正

2026-11-24，CMM-AL00，MNN ARM CPU，VAE CPU Low／6线程，原W8/group64权重。

## 为什么原120秒测试仍慢

上一轮120秒链路总1090.618秒／RTF9.088，其中LLM703.256秒，VAE174.742秒。
该轮较大模型未启用融合：旧App仅允许`choice0`（0.6B）使用Snake融合，且UI给较大模型显式传入false。
现在核对后确认，两套VAE原图及外部权重SHA256完全一致：

- 图：`c258bf4797bc2a1505c155a9d926e057d861045c56e2b9894192842f94ed9f89`
- 权重：`3b5e270d34e76de0c4322a88771f67e314e8192f5d3bd0cecd6760e8f6d5e1bc`

v0.1.15已把相同融合入口开放给较大模型，默认开启；保留`-VaeFusion 0`原版对照。
它是同一VAE的图／算子优化，没有更换checkpoint或另做有损量化。
仍强制CPU Low／6线程，逐一校验36处Snake拓扑与系数；不能静默回退后仍声称已融合。

## 较大模型真实latent对照

先冷却540.079秒，运行15秒完整较大模型链路，保存首窗真实VAE输入（64×256 float32，64KiB）。
使用同一二进制、同一输入和同一外部权重，独立原版／融合会话各前向4次；首轮与后三轮预热均值分开。
模块前后手机保持AWAKE，无屏幕关闭事件。顺序为原版后融合，不把它当作温度完全一致的随机交叉实验。

| 指标 | 原版 | 融合 |
|---|---:|---:|
| 首次前向＋同步 | 5.085秒 | 4.654秒 |
| **预热后平均** | **5.522秒** | **4.952秒** |
| 每次融合节点实际调用 | 0 | 36 |
| 同输入PCM | 参考 | **逐字节一致，L2=0，最大绝对误差=0** |

单窗为10.24秒双声道音频，模块耗时降低 **10.32%**，加速比 **1.115×**。
每个会话内部重复输出也完全一致；无算子回调、激活快照或在线校准混入前向时间。
权重不变，36组链移除144个逐点节点；减少的是中间激活处理，不等于整个VAE计算或DRAM流量降低同一比例。

## W4A8为什么仍不能保证低RTF

LLM主体W4／头W8，线性层采用动态激活量化；Norm、Attention等仍为混合精度，且解码逐token依赖前一步。
原120秒纯decode673.651秒，占LLM阶段约95.8%；prefill仅14.033秒。
短15秒与长120秒的上下文长度、热状态不同，不能把108.87与224.55ms/token的差全部归因于某个因素。

当前Runtime配置显式`cosyvoice_kleidiai=false`。所用本地MNN的`Llm::setRuntimeHint`
将它映射到`CPU_ENABLE_KLEIDIAI=0`，因此未请求KleidiAI专用分支。
本地CPU工厂的低内存量化分支仍可使用`DenseConvInt8TiledExecutor`，不能据此说没有量化或没有SIMD。
这些是配置和源码路径核对，不是逐算子运行时内核审计；本次VAE对照没有同时修改LLM配置。
